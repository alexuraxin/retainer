Autonomy

how far the agent goes on its own
Autonomy autonomy_level works
How much of the work the agent does without asking: tasks, branches, commits, pull requests, merge. Not about calling tools — that is further down.
manual — does nothing by itself, only on your command.
assisted — does, but asks permission every time.
auto — acts by itself, asks only on contested points.
marathon — a long run without you: stops nowhere, merges green pull requests itself and asks no questions. A fork in the work becomes a separate task with the chosen default, and the work goes on. Checks and review stay.

Git flow by step

issue · branch · commit · PR · merge · cleanup
off — I do not do it · ask — I propose, wait for "ok" · auto — I do it myself. If you leave a step alone, it follows "Autonomy" above; clicking the chosen value again clears it and returns the step there. The "Ask you" and "Confirm understanding" rows are not git steps: the question itself is the subject of the step, so the positions are labelled with words.
File an issue flow_issue
A task in the tracker before any work starts.
Branch flow_branch
A branch named after the task, issue-NNN, off the main branch.
Commits flow_commit
Commits that name their task.
Open a PR flow_pr
A pull request that closes its task when merged.
Merge flow_merge
Merge the PR. If you leave it alone, it is yours everywhere except marathon; there the agent merges itself, but only a green PR.
Cleanup flow_cleanup
Close the task, take off its working label, bring the main branch up to date.
Ask you flow_ask_owner
The right to stop work with a question. do not ask — there will be no questions at all: a fork goes out as a separate task with the chosen default. There is no third position here — "ask permission to ask" does not exist.
Confirm understanding flow_confirm_intake
Before starting, the agent writes in a line or two how it understood the task and waits for "ok". This is not about forks inside the work but about its boundaries — so it stays on even in a long autonomous run. straight to work — it starts without confirming.

When to call tools

review, plan check, browser test, second opinion
off — not used · ask — I propose and wait for "ok" · auto — I call it myself when needed.
Global mode
One setting for every tool, or each on its own.
"per tool" — each toggle below counts. "always propose" and "always by itself" make every tool ask or act by itself, except the ones switched off below.
Code reviewer tool_code_reviewer
Reads the diff before a commit. A merge needs a review record on the exact version being merged; who wrote it is not checked, so beyond that this is a recommendation.
Plan check tool_plan_checker
Checks the task plan before any code is written. A recommendation: nothing stops the code if the check is skipped.
Tester tool_tester
Opens changed pages in a real browser and clicks through them. A recommendation: nothing stops the work if it is skipped.
Second opinion tool_second_opinion
Asks another model before an important or irreversible step. A recommendation: nothing stops the work if it is skipped.
In a marathon nobody is there to answer "ask", so it turns into a decision:
tool_code_reviewer review always runs, whatever is chosen above
tool_plan_checker "ask" works as "auto": the plan is checked without asking
tool_tester "ask" works as "off": the browser test is skipped
tool_second_opinion "ask" works as "off": no second opinion is requested

Auto-continue

picks the work back up without you
Auto-continue …
Picks up tasks already in progress and restarts runs that failed or hit a usage limit.
Pause — stops new runs at once; a session already running is not interrupted. Safe to press at any moment. What to run and when is set up in the terminal, not here.

Extra checks
on top of the base; switching one off never goes below it


          

            
hooks_check

            

            
The project's git hooks are connected.

            
goes red when: the hooks are not connected, so nothing is checked before a commit or a push. Skipped in CI, which has no hooks of its own.

          


          

            
guard_registration

            

            
The guard is registered, so it really loads in a session.

            
goes red when: the guard is on disk but nothing registers it, or it is registered twice. Skipped in CI.

          


          

            
doc_links

            

            
Every path named in the agent's instructions exists.

            
goes red when: an instruction names a path the project does not have. Prose with a slash, like owner/repo, is not taken for a path; to skip a line, mark it with retainer:allow-link

          


          

            
agent_canon

            

            
Each agent role exists once: either the project's own or the shared one.

            
goes red when: the same role is defined in both places. Which one runs is then undefined, and an edit to the shared one may change nothing.

          


          

            
protected_copy

            

            
A protected file has no unprotected copy under another name.

            
goes red when: a copy of a protected file lies next to it under another name. The copy can be edited freely, so the protection means nothing.

          


          

            
bypass_alert

            

            
Repeated guard blocks do not go unnoticed.

            
goes red when: the same block repeats more often than the daily threshold. One block is normal work; repeats mean the rule needs a look.

          


          

            
hot_context

            

            
What the agent must read at the start of a session stays short and holds rules, not reports.

            
goes red when: it grows past the size limit or lists finished tasks.

          


          

            
remote_creds

            

            
The remote repository address carries no login, password or token.

            
goes red when: the address holds credentials: they sit there in plain text and outlive a password change. Only the remote's name is printed, never the value.

          


          

            
skills_catalog

            

            
The list of skills in the docs is built from the skills themselves.

            
goes red when: a description in the docs differs from the skill it describes.

          


          

            
doc_claims

            

            
A fact a document marks as checkable is checked by running the command next to it.

            
goes red when: the command next to a marked claim fails. Unmarked prose is not checked.

          


          

            
practices_form

            

            
A practice rule says where it was taken from (Sample: <file>:<line>) and when (Distilled: <date>).

            
goes red when: a rule changed in this branch has no source or no date. Untouched old rules are not judged; with no .retainer/practices.md the step is silent.

          


          

            
runner_labels

            

            
Every CI job asks for the same runner, the one the project declares.

            
goes red when: a job asks for another runner. Such a job never starts and waits in the queue forever, and whatever depends on it is silently off.

          


          

            
complexity_trace

            

            
A new code file (.py, .sh) states in one marked line why it is needed.

            
goes red when: a module or script added on this branch has no such line. Tests, docs and presets are exempt. Silent in a project whose main branch is not called main

          


          

            
prose_langneeds declaration

            

            
Comments, docstrings and names in code are written in Latin script. Text shown to users is not checked.

            
goes red when: new or changed code has Cyrillic in a comment, docstring or name; old code is not judged. To allow one line, mark it with retainer:allow-prose. Works only once the key is written into the project config, so an existing project does not go red on its first edit.

          


          

            
prototype_debtneeds declaration

            

            
Code knowingly left below the standard is marked in place with # prototype: #<task> — <what replaces it>, so the list of such debt is read from the code.

            
goes red when: a prototype marker has no task number, so nobody can find what was agreed. No markers — silent. Works only once the key is written into the project config.

          


          

            
glossary_termsneeds declaration

            

            
A term that code or docs refer to as :term:`Name` is defined in the project glossary.

            
goes red when: a reference points to a term the glossary does not have; case is ignored. No glossary or no references — silent; a glossary named in the config but not found is a refusal. Works only once the key is written into the project config.

          


          

            
deny_sync

            

            
The project's list of protected paths agrees with the paths the tools are forbidden to touch.

            
goes red when: a path is forbidden to the tools but missing from the project's list, so whoever reads the config thinks it is open. The reverse gap is reported on a line of its own.

          


          

            
dependency_check

            

            
Every library in the dependency list is actually installed.

            
goes red when: a listed library is not installed. A made-up name is a risk on its own: someone can register it and ship their code under it.

          


          

            

              

                
secret_scan

                
Looks for secrets committed into the repository.

              

              

                
                
                
              

            

            
off: not checked. basic: known key formats only (AWS, GitHub, Slack, JWT, PEM), almost no false alarms. thorough: also generic secret=… and password=… lines. A test secret is marked with # retainer:allow-secret

          


          

            

              

                
req_trace

                
Links each requirement to the code and tests tagged with it, like req: R-1

              

              

                
                
                
              

            

            
off: not checked. basic: lists uncovered requirements and stray tags; the gate stays green. thorough: the same, and the gate goes red. Requirements live in .retainer/requirements.md

          

        


        
        

          
Stack
turn on for the project's language


          

            
django_extras

            

            
Template formatting, Django's own check, missing migrations, and calculations kept free of web code.

            
goes red when: a template is not formatted, a migration is missing, or the calculation layer imports Django web code.

          


          

            
js_gate

            

            
Syntax check, lint and tests for JavaScript that runs outside the browser.

            
goes red when: such code has a syntax error, dead code or a shadowed name.

          

        

      


      
      

        

          
.retainer/config.toml
            
              
              
            
          

          

        

        
"Save" writes the checks of the project picked above into that project's own config file. Before a project is picked, this is a template to copy by hand. A check the project never declared stays undeclared unless you touch it here. By default for Python everything is on except the stack, with the secret scan and requirement links in basic mode.

      

    

  


  

    Settings for all projects live in ~/.config/retainer/config.toml; a project's checks live in its own .retainer/config.toml. The base checks ignore every switch on this page.
