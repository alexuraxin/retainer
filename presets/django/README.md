# Django module of the preset (optional)

Wired in on top of `presets/python/*` for Django projects. Non-Django Python projects
(scrapers, scoring, libraries) take only the base Python preset.

## What it adds

### 1. N+1 detector — `django-zeal`
The fixture is APPENDED to the same single `conftest.py` that carries the per-marker timeouts
(`presets/python/conftest.py.template`; it lies next to `pyproject.toml` — where pytest's rootdir is).
Do not create a separate conftest for Django: two files with run policy drift apart silently, and the one that
ends up above the rootdir pytest will not pick up at all — the fixture will not turn on, and N+1 will stop being
guarded without a word in the output. Trigger (skill `task-cycle`, step 0): a task adds a
screen or a queryset → zeal is enabled BEFORE the task, not after an incident.

```python
# into the same conftest.py, next to what is already there
import pytest
from zeal import zeal_context


@pytest.fixture(autouse=True)
def _zeal():
    with zeal_context():
        yield
```
⛔ `conftest.py` is under the guard: both zeal and the timeout are switched off with one line. An edit goes through
an unlock by the owner's key — like `pyproject.toml` and `.importlinter`. That is why the project's fixtures
live in `tests/plugins/`, and only their wiring and the run policy stay in conftest.

The detector also catches repeated assembly: if a use case reuses another use case as a whole, that one assembles
the same set again — and zeal declares N+1, failing the case. What should be reused is the shared assembly
component, not the use case: a use case has its own unit of work, and it cannot be nested in another without a double
read.

### 2. Django types — `django-stubs`
mypy strict with Django requires `django-stubs` + `django-stubs-ext` (a production dependency:
admin/forms generics work at runtime via `django_stubs_ext.monkeypatch()` in settings).

```toml
# add to pyproject.toml
[tool.mypy]
plugins = ["mypy_django_plugin.main"]
[tool.django-stubs]
django_settings_module = "<project>.settings"
```

### 3. post-commit: migrate + runserver
Uncomment the corresponding block in `presets/python/githooks/post-commit` — after
schema changes there is no need to bring the server up by hand. Logs — `app/runserver.log` (in `.gitignore`).

### 4. Migration hygiene (rules, not tooling)
- Any change to `models.py` → `makemigrations` + `migrate`, never touch the DB schema directly.
- Data migrations matching by name → scope to a specific parent object
  (`process__name=...`), not globally over the table: otherwise a second object with the same name gets someone else's category.

#### When a migration needs a test
`makemigrations --check` proves the migration was not forgotten; `lintmigrations` — that it does not break
schema compatibility. Neither proves that the DATA after it is correct. A migration test
is mandatory when there is:

- `RunPython` (a data migration) or `RunSQL`;
- `SeparateDatabaseAndState`;
- a backfill before `NOT NULL` or a unique constraint;
- a field type change (value conversion);
- a re-marking of relations (FK → M2M, changing `to`, splitting one table into two);
- its own reverse migration (`reverse_code`);
- any migration where the shape of ALREADY accumulated data matters.

An autogenerated addition of a nullable field or an index needs no separate test — there is nothing to
diverge from the data.

Tool: `django-test-migrations` (`migrator.apply_initial_migration` → data → `apply_tested_migration`),
added to the Django project's `requirements-dev.txt`.

### 4.1. The shape of a data migration and of its test

Kinds tied to the framework live here, not in the preset's shared forms. A migration that changes DATA
must carry three things, and each is checked by eye in review:

- **reverse code** — not `RunPython.noop` if the forward code set something: the rollback returns the field to
  the state it was taken from, and the test checks that;
- **a comment with the volume of production data** next to the query ("in production about four thousand such
  records, the update is safe"): the decision "is this safe in production" is made by this number, and
  after half a year it cannot be recovered from the code;
- **a decoding of numeric codes**, if they take part in the condition: `hiring_status__in=(2, 7)` is
  readable by nobody after half a year.

The model inside a migration is the historical one (`apps.get_model`), not imported: an imported model
carries the current fields, while the migration runs on the state of its time.

A migration test applies the previous one, prepares records with factories, applies the one under test — and compares the
FULL state, including the record that must not be touched. Then it applies the previous one again and
checks that the rollback returned everything as it was. Comparing the full state instead of selected fields is the same
principle as in the shared test layer: comparing values catches what the fixture happened to fill in.

### 5. A template variable that does not exist — `--fail-on-template-vars`
A typo in a variable name inside a template renders as an EMPTY string: the page looks whole, the test
is green, and in production the price, name or button disappears. The `pytest-django` flag turns this into a failure.

```toml
# add to pyproject.toml, addopts
"--fail-on-template-vars",
```

### 6. The price of a query — an SQL counter and "new objects"
The N+1 detector (`django-zeal`, item 1) catches lazy reloading. It does NOT see two other classes: "three more
queries than before" and "a record was created as a side effect". Both are caught by an assertion in the test itself.

```python
def test_vacancy_list_query_budget(
    client: Client,
    django_assert_num_queries: DjangoAssertNumQueries,
) -> None:
    """The vacancy list costs a fixed number of queries.

    Growth shows up in the diff instead of in production.
    """
    # Four queries: session, user, vacancy page, total count.
    with django_assert_num_queries(_EXPECTED_QUERIES):
        client.get('/vacancies/')
```

```python
# tests/plugins/django_queries.py — 'nothing was created' as an everyday tool
type AssertNoNewObjects = Callable[
    [type[models.Model]],
    contextlib.AbstractContextManager[None],
]


@pytest.fixture
def assert_no_new_objects() -> AssertNoNewObjects:
    """Assert that no object of the model appeared inside the block."""

    @contextlib.contextmanager
    def factory(model_type: type[models.Model]) -> Iterator[None]:
        manager = model_type._default_manager  # noqa: SLF001 - test-only reach
        old_count = manager.count()
        yield
        assert manager.count() == old_count

    return factory
```

The annotations here are not decoration: the preset's gate runs `mypy` in strict mode, and a function without a
return type turns it red. The examples themselves are fragments: names like `Client` and `models` are not
declared in them, and they do not compile as a whole; what is carried into a project is the shape, not the letters.

The number in `django_assert_num_queries` is a contract, not a measurement: an edit of it in a diff means the price
of the operation changed, and that is a decision somebody made.

### 7. Scales, admin and visibility of refusal

Where the decision lives and how types are split by layers — in the base preset
(`presets/python/forms/README.md`, section "Where the decision lives and where the form lives"). Here — what is
tied to the framework.

**A scale is an enum, not a tuple.** Condition: the scale is used by a layer that must not import
the model. Then a pure enum lives in the calculation layer, and the field is fed from it directly — a set of pairs
suits the field in any form, and the model has no list of its own:

```python
band = models.IntegerField(
    choices=[(item.value, item.name.lower()) for item in ScoreBand],
)
```

Without this condition the scale remains a model's list: creating a calculation layer, a second
list and a guarding case for it is three artifacts where one was enough.

A second list appears for its own reason: labels are needed next to the values, which the admin
shows, and access to them from the model. It does not inherit the pure enum (a list of values is not extended),
so it takes the values from it — and then only the COMPOSITION can diverge, and the case is placed on that.
Comparing values is useless: in the form below they match by construction, and a band added to the
pure enum and forgotten in the model's list would silently never reach the database:

```python
@enum.unique
class ScoreBand(enum.IntEnum):
    """Bands the domain reasons about."""

    WEAK = 1
    SOLID = 2


@final
class Candidate(models.Model):
    """A candidate as this project stores it."""

    class Bands(models.IntegerChoices):
        """The same bands as the database stores them."""

        WEAK = ScoreBand.WEAK, 'weak'
        SOLID = ScoreBand.SOLID, 'solid'

    band = models.IntegerField(choices=Bands.choices)
```

**A custom list filter in the admin does not crash the page.** Condition: a filter that parses the value
itself (a range, a date, a composite key). The standard field filter redirects the page away on an unfit value
itself, but a custom one is handed the string from the query as is — and any value from the address
bar reaches the parsing. An unknown value neither narrows the selection nor breaks the page, and a range
is set with explicit boundaries, not by parsing a string.

**A refusal on invalid input does not vanish silently.** Condition: a response rendered into an already open
page — a partial response, a fragment, a response to a background request. Such a response has neither an error
page nor a redirect, so an explicit entry into the error tracker is placed before the refusal. Without it a broken
request is visible nowhere: the user sees an empty place, and there is nothing in the logs.

**A model and its admin travel together.** Condition: someone reads the model's records in production; an intermediate
relation table and an internal queue do not fall under the rule. The framework itself has no check "the model is not registered in
the admin" — it is provided by a pluggable set of additional system checks, and
in the preset it is not wired in. So the rule is held by review: a model without an admin means the data
exists, but there is nothing to look at it with in production. Wiring in the set is a separate decision: a dependency does not
install itself.
